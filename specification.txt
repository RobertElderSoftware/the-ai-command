# ChatGPT CLI Multi-Part I/O Protocol (CIOP) — Version 1.0

## 1. Scope and goals

This document specifies **CIOP/1.0**, a byte-safe, low-ambiguity protocol for:

1) **Marshalling input** to the model as a sequence of sections representing:
- stdin
- zero or more files

2) **Unmarshalling output** from the model as a **single JSON array** of “operations” that:
- write to stdout, and/or
- overwrite one or more provided files

### Goals
- **Byte-safe** for arbitrary binary stdin and file contents.
- **Unambiguous** parsing (no sentinel collisions with payload bytes).
- **Verifiable**: recipient can confirm correct unmarshalling using length + SHA-256.
- **Extensible**: add encodings, add opcodes later without breaking old parsers.

### Non-goals
- Streaming; this is a single-request / single-response envelope.
- Partial file edits / patching (reserved for future opcodes).

---

## 2. Terminology

- **Section**: one input part (stdin or file).
- **Payload**: the bytes of a section.
- **Encoding** (input): how the payload is represented in the prompt text.
- **Operation** (output): a JSON object describing an action (stdout print or file overwrite).
- **SHA-256**: lowercase hex digest of the *raw bytes* of the payload (64 hex chars).

---

## 3. Input prompt format (CIOP/1.0)

The input to the API `.input()` is **UTF‑8 text** that contains:

1) A fixed **envelope header**
2) A sequence of **sections**
3) Optional additional human instructions (outside the formal envelope) are allowed, but **strongly discouraged**; if present they must not alter the meaning of the section contents.

### 3.1 Envelope header

The prompt MUST start with:

```
---BEGIN CIOP/1.0---
```

and MUST end with:

```
---END CIOP/1.0---
```

Everything between is part of the formal protocol.

### 3.2 Sections

Each section has:

- A **section header line** with metadata
- A **payload block** of exactly `length` bytes (after decoding according to `encoding`)
- A **payload terminator line** that is safe because it is placed *after* reading exactly `length` bytes, not used to find boundaries.

#### 3.2.1 Section header line

Each section begins with a single ASCII line:

```
---SECTION <source> <encoding> <length> <sha256> [<meta...>]---
```

Where:

- `<source>` is one of:
  - `STDIN`
  - `FILE`
- `<encoding>` is one of:
  - `utf-8`
  - `base64`
- `<length>` is a non-negative base-10 integer:
  - If `encoding=utf-8`: number of bytes of the UTF‑8 payload text.
  - If `encoding=base64`: number of **raw decoded bytes** (not the base64 string length).
- `<sha256>` is SHA‑256 of the **raw decoded bytes**, lowercase hex.
- `[<meta...>]` is optional key/value metadata:
  - For `FILE`, `path=<path>` is REQUIRED.
  - For `STDIN`, no meta is required (meta MAY be present for future use).

**Examples of header lines**
- `---SECTION STDIN utf-8 12 e3b0...---` (example digest placeholder)
- `---SECTION FILE base64 256 abcd... path=src/Main.bin---`

#### 3.2.2 Payload block

Immediately following the header line:

- The payload representation begins on the next line.
- The payload representation is:
  - For `utf-8`: literal UTF‑8 text bytes of length `<length>` (this can include newlines).
  - For `base64`: base64 text that decodes to exactly `<length>` bytes.
- After the payload bytes (decoded), the sender writes a newline, then the terminator line.

#### 3.2.3 Terminator line

After the payload, the sender MUST include:

```
---END SECTION---
```

**Important**: the parser MUST NOT search for this terminator to delimit payload. It exists only as a human/debugging aid. The payload boundary is determined by `<length>`.

### 3.3 Verification rules (recipient/model side)

For each section:
1) Decode payload according to `<encoding>`.
2) Verify:
   - decoded byte length == `<length>`
   - SHA-256(decoded bytes) == `<sha256>`
3) If verification fails, the model SHOULD:
   - produce a stdout operation describing the mismatch, and
   - avoid destructive file writes unless explicitly safe.

This provides the “certainty” check missing from the prior marker-based design.

### 3.4 Encoding registry (extensible)

CIOP maintains an encoding token registry. CIOP/1.0 defines:

- `utf-8`: payload is raw UTF‑8 bytes (no transformation)
- `base64`: payload is RFC 4648 base64 text representing raw bytes
- `missing`: used in the case where a file is supplied as an argument, but the file is missing.  This allows for disambiguation between an empty 0 length file, and a non-existent file.

Future versions MAY add: `utf-16le`, `iso-8859-1`, etc. Unknown encodings MUST be treated as an error by strict parsers; tolerant recipients MAY respond with an error operation to stdout.

## 4. Output response format (operations JSON)

The model response MUST be **exactly one JSON value**:
- a top-level **array** of operation objects
- with no leading/trailing commentary text

### 4.1 Operation object common fields

Each operation object MUST contain:

- `"op"`: string opcode
- `"encoding"`: string encoding of `"data"` (currently: `"utf-8"` or `"base64"`)
- `"data"`: string payload in the specified encoding

Optionally (recommended):
- `"length"`: integer length in bytes of decoded data
- `"sha256"`: lowercase hex digest of decoded data

Including `length` and `sha256` makes output verifiable and aligns with input.

### 4.2 Supported opcodes (CIOP/1.0)

#### 4.2.1 `stdout`
Print decoded `"data"` bytes to standard output.

Required fields:
- `"op": "stdout"`
- `"encoding"`
- `"data"`

Optional:
- `"length"`, `"sha256"`

#### 4.2.2 `file_write`
Overwrite the entire target file with decoded `"data"` bytes.

Required fields:
- `"op": "file_write"`
- `"path"`: string path (MUST exactly match one of the provided FILE section `path=` values)
- `"encoding"`
- `"data"`

Optional:
- `"length"`, `"sha256"`

NOTE:  In the implementation of the client that executes the op code for the 'file_write' operation, the client must be written in such a way that makes it impossible for the client to write to any file other than ones that were supplied to the program as arguments.  It should never be possible for the LLM to return output that would 'inject' data into arbitrary files in the filesystem that were not supplied as arguments.

### 4.3 Ordering and multiplicity

- The array MAY contain multiple operations.
- The CLI SHOULD apply them **in array order**.
- Multiple `stdout` operations are allowed (they concatenate in order).
- Multiple `file_write` operations to the same path are allowed; last write wins (but discouraged).
- If no `stdout` op is present, the CLI prints nothing.

### 4.4 Output encoding rules

- If output bytes are not valid UTF‑8 or may be binary, use `"encoding":"base64"`.
- For `"utf-8"`, `"data"` is a JSON string containing Unicode; decoding to bytes uses UTF‑8.

---

## 5. Error handling recommendations

### 5.1 Input verification failure (model side)
If any section fails length/hash verification, respond with:

- a `stdout` operation describing which section failed and why
- avoid `file_write` unless explicitly requested and safe

### 5.2 Output verification failure (CLI side)
If the CLI chooses to verify `"length"`/`"sha256"` (recommended when present):
- If mismatch, abort file writes and print an error to stderr.

(Verification fields are optional in CIOP/1.0, but recommended.)

## 6. Examples (raw prompts and expected outputs)

Notes for examples:
- Hashes shown as `sha256:...` may be abbreviated with `…` for readability; in real traffic they are 64 hex chars.
- Lengths must match the decoded bytes. In a real test suite, compute exact values; here they are illustrative but structurally correct.
- Examples partition input space: utf-8 vs base64, zero files vs multiple, empty payloads, binary data, missing writes, multi-op stdout, etc.

## 7. Summary of why this fixes the original flaws

- **No marker collision ambiguity**: payload boundaries are determined by **byte length**, not sentinel searching; base64 is used for arbitrary bytes.
- **Less brittle parsing**: headers are one line; payload is length-delimited; output is pure JSON.
- **Verifiable unmarshalling**: SHA‑256 + length allow certainty checks.
- **Extensible**: encoding registry and opcode `"op"` design support future additions (new encodings, new operations) without changing the core framing.

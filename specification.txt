# ChatGPT CLI Multi-Part I/O Protocol (CIOP) — Version 1.0

## 1. Scope

CIOP/1.0 marshals stdin and files to a model and unmarshals a single JSON array of operations. Supported output operations print bytes, overwrite a writable file, or patch selected lines of a writable UTF-8 file.

The protocol is byte-safe, length-delimited, verifiable, and extensible. Input files and output paths are relative to the application's working directory. Implementations must reject absolute paths, parent traversal, symlinks, and paths resolving outside that directory. Paths must not contain control characters or the header delimiter `---`.

## 2. Input envelope

The complete prompt begins with `---BEGIN CIOP/1.0---` and ends with `---END CIOP/1.0---`. No instructions are appended outside the envelope.

STDIN sections have this header:

`---SECTION STDIN <encoding> <length> <sha256>---`

FILE sections have this header:

`---SECTION FILE <encoding> <length> <sha256> access=<READ|READ_WRITE> path=<path>---`

Encoding is `utf-8`, `base64`, or, for a nonexistent writable file, `missing`. Length and SHA-256 describe decoded raw bytes. A missing file has length zero, the SHA-256 of empty bytes, and an empty payload. FILE paths retain the exact spelling of their first included entry. The path is the last metadata field and extends to the closing header delimiter; spaces in filenames are allowed. Access is mandatory: READ means read-only; READ_WRITE permits file_write and file_patch, subject to their other rules. Never modify a READ file.

Payload boundaries are determined by byte length, not by searching for marker text. UTF-8 lengths count encoded bytes, not characters. Base64 payload length is derived from the decoded byte length. A framing newline and `---END SECTION---` follow the payload. Marker-like text or non-text bytes may be transmitted using base64. Verify decoded bytes using the declared length and SHA-256.

The first FILE is always the built-in, READ-only virtual document `__ciop__/CIOP_PROTOCOL_INSTRUCTIONS.txt`: this protocol specification, packaged as an application resource. It is not a project file or a writable destination. The entire `__ciop__` namespace is reserved. Read and follow this document when producing the response.

The remaining order is context files, additional command-line files, then STDIN. The context configuration itself is not transmitted unless explicitly included.

### 2.1 Context configuration

The optional `--context path` or `--context=path` argument loads a UTF-8 JSON document:

```json
{
  "files": [
    {"README.md": "READ"},
    {"src/example.txt": "READ_WRITE"}
  ]
}
```

The only top-level field is the required `files` array. Each array entry contains exactly one filename and one explicit, case-sensitive access string: READ or READ_WRITE. Unknown access strings, nulls, malformed JSON, duplicate object members, and extra fields are errors. An empty context is `{"files":[]}`. Without --context, an empty context is used; there is no automatic context.json discovery.

Both the context filename and every listed filename resolve relative to the application's working directory, not the directory containing the context configuration. READ files must exist and be regular files. Missing READ_WRITE files are valid creation targets. Directories are not file entries. All paths undergo the same containment and no-symlink checks.

Array order is preserved. Duplicate filesystem identities within context are errors, including normalized aliases such as `notes.txt` and `./notes.txt` and existing hard-link aliases. Command-line duplicates are sent only once and never upgrade a context permission. New command-line entries follow in argument order and default to READ_WRITE for compatibility. The first entry's transmitted path remains authoritative.

## 3. Output

The model response must be exactly one top-level JSON array, with no surrounding prose or Markdown fences. Operations are evaluated in array order.

### 3.1 stdout

`{"op":"stdout","encoding":"utf-8","data":"text"}`

Required fields are `op`, `encoding`, and `data`. Encoding is `utf-8` or `base64`. Optional `length` and `sha256` fields verify decoded bytes.

### 3.2 file_write

`{"op":"file_write","path":"notes.txt","encoding":"utf-8","data":"replacement\n"}`

This overwrites an entire file or creates a missing file. `path` must exactly match a READ_WRITE FILE section path. Required fields are `op`, `path`, `encoding`, and `data`. Optional `length` and `sha256` fields verify decoded bytes. Use base64 for binary or non-UTF-8 content.

### 3.3 file_patch

file_patch changes selected lines in an existing UTF-8 text file. Its JSON structure is intentionally explicit so models do not need to generate or escape unified-diff text.

Example replacement:

```json
{
  "op": "file_patch",
  "path": "notes.txt",
  "source_sha256": "<64 lowercase hex characters>",
  "hunks": [
    {
      "old_start": 2,
      "old_count": 1,
      "new_start": 2,
      "new_count": 1,
      "lines": [
        {"type": "remove", "text": "old line"},
        {"type": "add", "text": "new line"}
      ]
    }
  ],
  "result_sha256": "<optional hash of resulting UTF-8 bytes>",
  "final_newline": true
}
```

Rules:

- `path` must exactly match a READ_WRITE FILE path and name a regular file existing in the staged file view.
- `source_sha256` is required and must match that file's bytes when the operation is evaluated.
- Line numbers are one-based.
- Line `text` excludes `\n` and `\r` terminators.
- A `context` line consumes one old line and produces the same new line.
- A `remove` line consumes one old line and produces none.
- An `add` line consumes no old line and produces one new line.
- `old_count` equals the number of context plus remove lines.
- `new_count` equals the number of context plus add lines.
- Context and removed text must exactly match the source file.
- Hunks must be ordered, non-overlapping, and within the source range.
- `new_start` must identify the hunk's actual position in the progressively constructed result.
- `result_sha256` is optional. When present, it must match the complete resulting bytes.
- `final_newline` is optional and defaults to the source file's final-newline state.
- UTF-8 patch results use `\n` line endings. Use file_write when exact preservation of other line endings is required.
- Validation completes before replacement. Invalid hunks, stale hashes, unsafe paths, or result-hash mismatches reject the batch before destination changes.

Insertion before line 2 uses old_start:2, old_count:0, new_start:2, new_count:1, with one add line. Deletion uses one or more remove lines and new_count:0. Multiple hunks are evaluated in order against the original file while the result is built.

## 4. Ordering and safety

A patch following a write or earlier patch observes the preceding staged result, so its source_sha256 must describe that state. Multiple stdout operations concatenate their bytes.

Implementations enforce READ/READ_WRITE permissions, exact writable-path allowlisting, canonical containment, and no-symlink checks for both file_write and file_patch. Aliases must not bypass READ protection. Reserved protocol paths are never writable. File permissions are enforced by the application, independently of model compliance.

### 4.1 Batch validation and recovery

The complete response is parsed and validated against an in-memory file view before destination files, directories, or stdout change. A file created by an earlier file_write can be patched later in the batch. Normalized aliases share staged content; distinct hard-linked destinations and conflicting file/directory destinations are rejected.

Original bytes and file identities are rechecked before commit. Each destination receives its final staged bytes once. Existing files use sibling temporary replacement and atomic move where supported, preserving POSIX permission bits where supported; other metadata and hard-link relationships are not guaranteed to be preserved. Staging and recovery snapshots remain in memory. Ordinary commit failures trigger best-effort restoration of attempted destinations, deletion of newly created files, and removal of empty directories created by the batch. Recovery failures are reported individually. This is not crash-safe multi-file atomicity, and external concurrent modifications remain a race.

Stdout is buffered in operation order and published only after successful file commits. An output failure reports that files were committed and stdout may be incomplete; it does not roll back committed files. Never automatically retry such a batch. Prompt and response logging remains independent of staging and may occur even when validation rejects the batch.

## 5. Verification failures

Input length or hash failures should produce a stdout operation explaining the mismatch and avoid unsafe writes. Output length, output hash, patch source hash, patch content, or patch result hash failures reject the complete batch during validation without destination-file or stdout effects.

## 6. Guidance for models

Return only the JSON array. Use stdout for user-facing text. Use file_write for new files, binary files, or whole-file replacement. Use file_patch for a small line-oriented edit to an existing UTF-8 file. Copy context and removed lines exactly from the supplied FILE section. Keep hunks simple, ordered, and non-overlapping. Only READ_WRITE files may be changed, and output paths must exactly match their transmitted paths. The built-in protocol document is always READ-only.
